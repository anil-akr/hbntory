1. Le projet en 30 secondes

hbntory gère l'inventaire d'une entreprise de retail à plusieurs boutiques. Deux faces :

  • Un Backoffice (interne, avec login) : les employés gèrent le stock de leur boutique, l'admin gère les utilisateurs.
  • Une interface publique : n'importe qui pose une question en langage naturel sur les produits et le stock, et un agent IA répond — sans jamais inventer, uniquement à partir de vraies données.

Particularité : les infos produit ne nous appartiennent pas. Elles viennent d'une API Produit externe (fournie). On ne stocke jamais les détails produit ; on les récupère à la demande.

Analogie simple (pour bien comprendre)

  • API Produit = le catalogue du fournisseur : on le consulte, on ne le recopie pas (sinon nos prix seraient faux le jour où il les change).
  • Notre base de données = notre cahier de stock : « à Lyon, 5 exemplaires du produit HB-LAP-1001 ». Juste ça.
  • L'agent IA = l'hôtesse d'accueil : elle regarde les infos et répond, elle ne devine jamais.

4. Le voyage d'UNE question (à raconter en démo)

Question : « Quelle boutique a du HB-LAP-1001 ? »

[1] Client ───── "Quelle boutique a du HB-LAP-1001 ?" ─────▶ Service IA [2] Service IA ──── question + liste des outils ────▶ Modèle (Groq / Llama) [3] Le modèle réfléchit : « Je ne connais pas le stock → il faut appeler un outil. » Réponse : APPELLE stock_for_product(sku="HB-LAP-1001") [4] Service IA ──── appelle l'outil ────▶ Serveur MCP ──── lit le stock [5] MCP renvoie les VRAIES données : { Paris:12, Lyon:5, Marseille:3 } [6] Service IA ──── "voici le résultat" ────▶ Modèle [7] Le modèle rédige la réponse, UNIQUEMENT avec ces chiffres : « HB-LAP-1001 est dispo à Paris (12), Lyon (5) et Marseille (3). » [8] Service IA ──── la réponse ────▶ Client
Le point fort à souligner : à l'étape [3] le modèle ne connaît pas les stocks — il demande un outil. À l'étape [7] il ne répond qu'avec ce que l'outil a renvoyé. Il ne peut donc pas inventer. C'est une réponse « ancrée » (grounded).

5. Les décisions techniques — le « pourquoi »

Le jury évalue surtout votre capacité à justifier. Formule chaque décision : choix → parce que → compromis.

① Des services séparés (Backoffice ≠ Service IA)

Parce que : deux publics (interne authentifié vs public anonyme), donc deux responsabilités. On peut les développer/tester/déployer séparément. Compromis : plus de services à orchestrer → résolu avec Docker Compose.

② Un serveur MCP comme « boîte à outils » de l'IA

MCP (Model Context Protocol) = un standard pour exposer des outils à un agent IA. L'agent appuie sur un bouton, sans savoir ce qu'il y a derrière.

Parce que : ça isole l'IA des sources de données (sécurité + propreté), et si la source change, seul le « derrière du bouton » change. Exemple : demain le stock passe du fichier JSON à la vraie base de Marie → l'agent continue d'appeler le même outil stock_for_product, on ne touche pas à l'IA. Compromis : une brique de plus à écrire.

③ On ne stocke jamais les détails produit

Parce que : les produits appartiennent à l'API externe ; les dupliquer = incohérences. Exemple : le fournisseur baisse le laptop à 699 $ mais notre base dit 799 $ → faux prix affiché. On ne garde que le SKU pour relier le stock. Compromis : il faut appeler l'API pour un nom/prix (acceptable, et c'est la contrainte de l'énoncé).

④ Stock relié au produit par le SKU, pas par l'id

Parce que : le sku (HB-LAP-1001) est un identifiant métier stable ; l'id numérique peut changer si le catalogue est reconstruit → le stock pointerait vers le mauvais produit.

⑤ Choix de communication

LiaisonChoixParce que / compromis
BackofficeREST + HTML/CSS/JSFront dynamique + API structurée. Compromis : plus de travail qu'un rendu serveur.
Client ↔ IARESTChaque question est indépendante (pas d'historique) → REST suffit, simple à tester. Compromis : pas de streaming. WebSocket ne servirait qu'au temps réel, inutile ici.
IA ↔ MCPStreamable HTTPLe MCP reste un service indépendant (son conteneur). Compromis : un peu plus de config que le mode sous-processus (stdio).

⑥ L'IA accède au stock via NOTRE MCP

Parce que : on étend notre propre MCP avec des outils de stock plutôt qu'un MCP tiers de base de données. Un seul composant, une frontière contrôlée, l'IA ne voit jamais la base. Compromis : on écrit ces outils nous-mêmes.

⑦ Agent agnostique du modèle

Parce que : seul agent.py dépend du fournisseur d'IA. On a migré Anthropic → Gemini → Groq en ne changeant que ce fichier. Preuve d'une bonne séparation des responsabilités.

6. Le serveur MCP en détail (Anil)

Un seul fichier product_mcp_server/server.py ; chaque fonction @mcp.tool() = un outil. Streamable HTTP sur :8000/mcp, appels réseau en urllib (bibliothèque standard).

OutilRôleSource
list_productsLister / rechercher des produitsAPI externe
get_productDétails d'un produit (par SKU)API externe
stock_for_productDans quelles boutiques un produit est dispostock
stock_in_branchCe qu'une boutique a en stockstock
check_shopping_listQuelle(s) boutique(s) pour une liste d'achatsstock

Gestion des erreurs (jamais d'échec silencieux)

Toute la logique réseau passe par une seule fonction _get_json() :

SituationMessage clair renvoyé
Produit inexistant (404)« Product not found in the catalog. »
API en erreur (autre code)« The Product API responded with status N. »
API injoignable / timeout« The Product API is unreachable. »

Le cas malin : check_shopping_list

Répond au « quelle(s) boutique(s) » (pluriel) de l'énoncé. Renvoie : fully_satisfied_by (boutiques qui suffisent seules), plan (combinaison de boutiques à visiter — algo glouton : d'abord là où il y a le plus de ce qui manque), et satisfiable/missing (si le réseau entier ne suffit pas).

7. L'agent IA : la boucle d'outils (Anil)

Fichier ai_service/agent.py. Le concept central :

tant que (le modèle demande un outil):
    exécuter l'outil via le MCP
    renvoyer le résultat au modèle
sinon:
    renvoyer la réponse texte finale
  • Prompt système : « n'utilise que les données des outils, n'invente jamais, dis si l'info manque » → le garde-fou.
  • Observabilité : on affiche chaque [tool call] → on voit en direct quels outils l'agent utilise (à montrer en démo !).
  • Boucle bornée : MAX_TOOL_ROUNDS = 5 → jamais de boucle infinie.
  • Endpoint (app.py) : Flask POST /ask, en-têtes CORS (le front est sur un autre port), et en cas d'échec → 502 + message JSON clair.
À assumer honnêtement (le stock) : les outils de stock lisent aujourd'hui un fichier stock_data.json qui remplace temporairement la base de Marie. À l'intégration, seule _load_branches() change — outils et formats identiques, l'agent n'est pas impacté. Ce n'est pas un défaut : c'est justement la force du MCP (la source est cachée derrière l'outil).

10. Questions probables du jury + réponses

C'est quoi MCP, et pourquoi pas une simple API ?

MCP est un standard pour exposer des outils à un agent IA. Vs une API classique : l'agent découvre les outils et décide quand les appeler. Ça isole l'IA des sources de données et rend les outils réutilisables.

Comment empêchez-vous l'IA d'inventer ?

(1) prompt système strict « uniquement les outils, jamais inventer » ; (2) l'agent n'a aucune donnée en lui, il doit appeler un outil pour tout ; (3) si l'info manque, il le dit. Démontré par la question hors-sujet.

Pourquoi REST et pas WebSocket pour le client ?

Chaque question est indépendante, sans historique → REST suffit (1 requête / 1 réponse), simple à tester. WebSocket ne se justifie que pour du temps réel/streaming, inutile ici.

Pourquoi Streamable HTTP pour le MCP et pas stdio ?

Pour garder le MCP comme service indépendant (son conteneur), joignable sur le réseau. stdio l'aurait enfermé comme sous-processus du Service IA.

Que se passe-t-il si l'API Produit tombe ?

Pas de plantage silencieux : _get_json attrape l'erreur et renvoie « API injoignable » ; l'endpoint renvoie un 502 avec un message clair.

Comment l'IA accède au stock ? Pourquoi un fichier JSON ?

Via des outils de notre MCP (jamais la base en direct). Le fichier remplace la base partagée le temps de l'intégration ; on ne change qu'une fonction pour brancher la vraie base. C'est l'avantage du MCP : la source est cachée derrière l'outil.

Pourquoi bcrypt pour les mots de passe ?

Algorithme lent et adaptatif, avec sel intégré → brute-force très coûteux. On ne stocke jamais le mot de passe en clair, seulement son empreinte.

Comment les autorisations sont-elles appliquées ?

Côté backend : un utilisateur commun n'agit que sur sa boutique, l'admin ne gère que les utilisateurs. Cacher un bouton ne suffit pas ; la règle est vérifiée sur le serveur.

Le stock peut-il devenir négatif ?

Non : CHECK quantity >= 0 en base (dernier rempart) + validation applicative avant l'opération.

Comment gérez-vous les secrets (clés API) ?

Clé dans un .env gitignoré (jamais sur GitHub), chacun sa clé, lue depuis l'environnement.

Vous pouvez changer de modèle IA facilement ?

Oui — seul agent.py dépend du fournisseur. Migré Anthropic → Gemini → Groq sans toucher au reste.

Pourquoi Groq / Llama ?

Gratuit, sans carte, rapide, et compatible « function calling » (indispensable à la boucle d'outils). Et changeable en 5 min grâce à l'archi agnostique.
